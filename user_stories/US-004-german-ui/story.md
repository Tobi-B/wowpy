# US-004 — German user interface

> **Status: documented only — not scheduled, not part of the backlog.**
> Written on request so the decisions and the pitfalls are not lost. Do not
> start implementing this story unless the user asks for it explicitly.

**As a** German-speaking developer (and for German-speaking learners using the
robot),
**I want** the dashboard and the block editor in German,
**so that** blocks, buttons and the log read naturally without translating in my
head while programming.

## Scope

**Only the user interface.** Source code, docstrings, README, CLAUDE.md and the
user stories stay English.

| Confirmed | |
|---|---|
| Surface | GUI only — dashboard (`/`) and block editor (`/blocks`) |

| Assumed (stated, not contradicted — confirm before implementing) | |
|---|---|
| Language | Fixed German, no language switch. Making it switchable later stays possible. |
| Generated Python | Stays English: a block labelled "Brust-LED" still generates `await mip.set_chest_led(...)`, so the code matches the wowpy API. |

## The one rule that matters

**Translate labels, never values.** Several lookup tables in `wowpy/protocol.py`
serve two masters at once: they are shown in the UI *and* their strings appear as
literals in generated programs and in the runtime's event matching.

```python
# wowpy/blocks.py - dropdown for "when position becomes ..."
{"type": "field_dropdown", "name": "POS",
 "options": [[v, v] for v in p.POSITIONS.values()]}   # label == value today
```

```python
# generated by the editor
program.on_position(_on_position_h, position='face down' or None)
```

```python
# wowpy/program.py - matched against the decoded notification
p.POSITIONS.get(f.get("position")) == position
```

Translating `POSITIONS` itself would change the generated code, break every
saved program in `programs/`, break the matching in `program.py`, and break the
tests that assert on decoded text. Blockly dropdowns are `[label, value]` pairs,
so the fix is free: **German label, English canonical value.** The same applies
to game modes, head-LED states, gesture/radar modes, radar readings and gestures.

## Implementation sketch

A new `wowpy/i18n.py` holds the German labels; `protocol.py` keeps its English
canonical data untouched. Translation happens at the edges:

| What | Where it comes from today | How to translate |
|---|---|---|
| Block labels (~35) | `message` in `wowpy/blocks.py` | add `message_de`, serve it from `catalogue()` |
| Dropdown options | `_dropdown()` / `POSITIONS.values()` etc. | German label, canonical English value |
| Toolbox categories (14) | `TOOLBOX` in `blocks.py` + the extra categories in `blocks.html` | translate both lists |
| Command names (37) for the log | `Command.name` | `i18n.DE_COMMANDS[name]`, used only for display |
| Decoded reply text ("battery 100%, upright") | `decode_reply()` in `protocol.py` | render German from the structured `fields` in the hub, falling back to the English `text` |
| Status panel field labels | `FIELDS` in `index.html` | translate in place |
| Buttons, dialogs, hints, messages | both HTML pages | translate in place |
| Blockly's own blocks (Logic, Math, Text, Variables, Functions) | Blockly core | load `blockly/msg/de.js` from the CDN |

Everything the pages get from the API is already fetched at boot
(`/api/commands`, `/api/blocks/catalogue`), so no new endpoints are needed.

## Acceptance criteria

See `german-ui.feature`.

## Out of scope

- A language switch or any other locale than German.
- Translating generated Python, the wowpy API, file names in `programs/` and `blocks/`.
- Translating the shipped composite blocks' *names* (Celebrate, Patrol, …) —
  renaming them changes `blocks/*.json` and every program using them; a separate
  decision.
- Docstrings, README, CLAUDE.md, user stories.
